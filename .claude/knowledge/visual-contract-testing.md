# 시각 계약을 jsdom에서 정직하게 테스트하는 법

확정일: 2026-08-18 (T08 / `/code-review xhigh` 후속)

## 문제

jsdom에는 레이아웃 엔진이 없고 vitest 설정도 `css: false`다. 그래서 "이 화면이 제대로 보이는가"를 검증하려다 **`App.css` 원문을 정규식으로 훑는** 테스트가 만들어졌다. 이 방식은 두 방향 모두로 틀렸다.

- **거짓 실패**: `display: grid`와 `grid-template-rows` 선언 **순서만** 바꿔도 실패한다. `16px` → `1rem` 같은 no-op 편집도 실패한다.
- **거짓 통과**: 화살표가 62px 어긋나고, 화살촉이 투명하고, 모바일이 가로로 넘치고, 차트 막대가 뭉개져도 전부 통과했다.

## 결정

시각 계약을 세 층으로 나눠서 각각 검증 가능한 형태로 만든다.

### 1. 좌표는 순수 함수로 뽑아 픽셀 단위로 테스트한다

컴포넌트가 컨테이너를 측정해 픽셀 좌표를 계산하게 하고, 계산 자체는 `src/domain/`의 순수 함수에 둔다. 그러면 "화살표가 노드에 닿는가"가 숫자 비교가 된다.

**정규화 좌표계와 픽셀 배치를 섞지 말 것.** `<svg viewBox="0 0 100 100">`는 기본 `preserveAspectRatio`로 균등 축소·중앙 정렬되므로, `left: x*100%`로 배치된 형제 레이어와 절대 맞지 않는다. 정사각형이 아닌 컨테이너에서는 반드시 어긋난다.

### 2. CSS는 캐스케이드를 계산해서 검증한다 (`src/test/cssModel.ts`)

원문 매칭 대신 **누가 이기는가**를 계산한다.

```ts
resolveDeclaredValue(element, 'grid-column', rules, { viewportWidth: 390 })
```

- 선택자 매칭은 **jsdom(nwsapi)의 `Element.matches`에 맡긴다.** 직접 구현하지 않는다.
- 직접 계산하는 것은 특이도 `[id, class, type]`와 **소스 순서**뿐이다.
- `@media`는 특이도를 더하지 않는다. 파서는 파일을 한 번만 훑으며 **실제 소스 순서를 보존**해야 한다. 최상위 규칙을 앞으로 재정렬하면 "나중에 나온 최상위 규칙이 @media를 이긴다"는 실제 동작과 어긋난다.

이 모델로 세 종류의 결함을 잡을 수 있다.

- 특이도에 밀려 **죽은 선언** (`.edges path` vs `.edge-arrowhead`)
- 효과 없는 **@media 오버라이드** (`.constellation{height:680px}`가 `.trading-main .constellation`에 패배)
- 같은 선택자를 멀리 떨어진 두 곳에서 선언해 **앞쪽이 사장**되는 경우

### 3. jsdom에 렌더 박스를 주입한다 (`src/test/layoutBox.ts`)

```ts
useFakeElementBox({ constellation: { width: 720, height: 470 } })
```

`getBoundingClientRect`를 클래스 기준으로 갈아끼운다. 주입하는 값은 **CSS가 실제로 강제하는 값**과 맞춰야 한다 — `min-width: 720px`가 있으면 720을 넣는다. 아무 숫자나 넣으면 테스트가 현실과 무관해진다.

## 테스트를 쓸 때 지키는 것

- **회귀 가드와 결함 수정을 구분해 기록한다.** 처음부터 통과한 테스트는 결함을 잡아 만든 것이 아니다.
- **테스트가 곧바로 통과하면 테스트를 의심한다.** T08에서 autonomy 클램프 테스트가 그랬다 — 기본 선택 에이전트만으로는 클램프 구간에 닿지 않아, 전 에이전트를 순회하도록 넓히고 나서야 실패했다.
- **계약을 좁게 쓰지 말 것.** "두 중심을 잇는 직선 위에 끝점이 있다"는 곡선 우회를 금지해 버린다. "각 끝점이 자기 노드 카드 경계에 붙어 있다"가 같은 버그를 잡으면서 구현을 덜 묶는다.
- **일반 불변식이 프로젝트 구조와 충돌하면 좁힌다.** "같은 선택자에 같은 속성을 두 번 선언하지 않는다"를 전역에 걸었더니 약 30건이 나왔는데, 대부분 "기본 테마 + Trading Room 리스킨"이라는 **의도된** 오버라이드 레이어였다. 규칙을 문제가 실재하는 선택자로 좁혔다.

## 캐스케이드로 증명할 수 없는 것

**z-index가 실제로 무언가를 정렬하는가**는 캐스케이드만으로 판정할 수 없다. 스택 컨텍스트 소속은 모델링할 수 있지만(`stackingContextOf`), 두 엘리먼트가 화면에서 겹치는지는 레이아웃 정보다.

주의: `contain: layout paint`는 그 엘리먼트 **자신**이 스택 컨텍스트를 만들 뿐, 그 엘리먼트가 부모 컨텍스트에서 자기 z-index로 정렬되는 것은 막지 않는다.
